Manual de Contingencias

Errores comunes en despliegue de aplicaciones web y cómo resolverlos

Cómo usar este manual: cada caso está armado como Síntoma → Causa → Solución. Buscá primero por lo que ves en pantalla (el error literal), no por lo que creés que está mal — la mayoría de estos errores tienen una causa distinta a la que parece a primera vista.

Está basado en incidentes reales resueltos durante despliegues propios, no es una lista genérica copiada de internet.

1. Variables de entorno no coinciden entre archivos

password authentication failed for user "..."

Crítico

Síntoma

El backend entra en Restarting en bucle. Los logs muestran FATAL: password authentication failed (código Postgres 28P01).

Causa

Cuando el proyecto usa dos archivos .env distintos (uno para crear la base de datos, otro para que el backend se conecte a ella), Postgres solo lee la contraseña la primera vez que inicializa su volumen. Si después el otro archivo tiene un valor distinto — o quedó con el placeholder de la plantilla sin editar — el backend intenta entrar con una clave que no coincide.

Solución

Confirmar que las credenciales sean idénticas en ambos archivos:

grep -E "PGUSER|PGPASSWORD|PGDATABASE" .env
grep -E "PGUSER|PGPASSWORD|PGDATABASE" backend/.env.production

Si no coinciden, corregir uno de los dos. Si el volumen de la base ya se creó con la clave vieja, hay que resetear (solo seguro si no hay datos reales todavía):

docker compose -f docker-compose.prod.yml down -v
docker compose -f docker-compose.prod.yml up -d --build

  Prevención: editar la clave en un solo lugar y copiarla al otro archivo, nunca escribirla dos veces a mano.

2. Docker Compose rompe valores con signos $

The "XXXXX" variable is not set. Defaulting to a blank string.

Alto

Síntoma

Al levantar los contenedores aparecen warnings de variables "no definidas" cuyo nombre es un fragmento de una contraseña o hash (por ejemplo un hash de API o un bcrypt). La app funciona pero con ese dato vacío/roto (ej. login externo devuelve 401).

Causa

Docker Compose interpreta cualquier $algo dentro de un archivo .env como una variable a sustituir. Si el valor real contiene signos $ literales (hashes tipo bcrypt $2y$10$..., algunas claves generadas), Compose intenta reemplazarlos por una variable de entorno que no existe — y los deja en blanco.

Solución

Escapar cada $ literal como $$ dentro del archivo .env:

# Antes (se rompe):
TRACKING_API_URLS=...user_api_hash=$2y$10$GvpiFgLM...

# Después (correcto):
TRACKING_API_URLS=...user_api_hash=$$2y$$10$$GvpiFgLM...

Reconstruir el servicio afectado después de corregir:

docker compose -f docker-compose.prod.yml up -d --build backend

  Prevención: cualquier valor que use env_file: en Compose y tenga signos $ (hashes, algunas claves) necesita $$ desde el primer momento en que se escribe el archivo.

3. El build falla en producción pero funcionaba en desarrollo

Cannot find namespace 'JSX' / must be imported using a type-only import

Alto

Síntoma

El proyecto corre perfecto en desarrollo (npm run dev), pero docker build falla al ejecutar npm run build con errores de TypeScript que nunca se vieron antes.

Causa

Cuando el proyecto usa "project references" en tsconfig.json (patrón típico de plantillas modernas de Vite), un chequeo rápido con tsc --noEmit sin la bandera -b no revisa nada en absoluto — da una falsa sensación de que todo compila. El comando real de build (tsc -b) sí aplica reglas más estrictas (como verbatimModuleSyntax) que nunca se probaron hasta ese momento.

Solución

Separar los imports de tipos de los de valores:

// Antes:
import { FormEvent, useState } from "react";

// Después:
import { useState } from "react";
import type { FormEvent } from "react";

Y reemplazar usos de JSX.Element por ReactElement (importado como tipo desde "react").

  Prevención: para chequear de verdad un proyecto con project references, usar npx tsc -b (no --noEmit a secas), o directamente correr npm run build localmente antes de cada despliegue.

4. Puerto ya ocupado / conflicto con otro proyecto

Bind for 0.0.0.0:XXXX failed: port is already allocated

Medio

Síntoma

Un servidor con varios proyectos Docker corriendo a la vez no deja levantar un contenedor nuevo porque el puerto elegido ya lo usa otro proyecto.

Causa

Elegir puertos "a mano" sin revisar antes qué hay ocupado, en un servidor que hostea múltiples clientes/proyectos.

Solución

Revisar qué está ocupado antes de asignar uno nuevo:

docker ps --format "table {{.Names}}\t{{.Ports}}"

Preferir no publicar puertos al host en absoluto cuando se puede enrutar por dominio (Traefik/Dokploy) o por un proxy interno — evita este problema de raíz.

  Prevención: si el servidor ya tiene un reverse proxy central (Dokploy, Traefik, nginx), usarlo para todo lo nuevo en vez de publicar puertos manualmente proyecto por proyecto.

5. YAML mal indentado o con claves duplicadas

yaml: construct errors: mapping key "X" already defined

Medio

Síntoma

Editar un docker-compose.yml manualmente (con nano o similar) y que el archivo quede con una sección repetida o mal alineada, rompiendo el parseo.

Causa

Ediciones manuales sucesivas sobre el mismo archivo, sin verificar el resultado final después de cada cambio — un mismo bloque termina pegado dos veces.

Solución

Reescribir el archivo completo de una sola vez con un heredoc en vez de editarlo a parches:

cat > docker-compose.prod.yml << 'EOF'
services:
  ...
EOF

Siempre verificar el resultado antes de usarlo:

cat -n docker-compose.prod.yml

  Prevención: después de cualquier edición manual de un YAML, releerlo completo antes de ejecutar el siguiente comando — no asumir que la edición se aplicó como se pidió.

6. La terminal rompe comandos al pegarlos (zsh)

invalid number of arguments in "proxy_pass" directive

Medio

Síntoma

Un archivo de configuración (nginx, por ejemplo) queda con caracteres agregados solos, típicamente una barra invertida antes de un punto y coma (\;), aunque el comando que se pegó no la tenía.

Causa

Zsh (con Oh My Zsh u otras configuraciones) trae una función de seguridad (url-quote-magic) que escapa automáticamente caracteres especiales cuando detecta que se está pegando algo con forma de URL. Esto ocurre al nivel del editor de línea de la terminal, antes de que el comando llegue a ejecutarse — así que hasta un heredoc bien escrito puede salir mal si se pega directo en una sesión zsh interactiva.

Solución

Arreglar la línea afectada con sed en vez de volver a pegar la URL (evita disparar la misma magia de nuevo):

sed -i 's/8092\\;/8092;/' /etc/nginx/sites-enabled/mi-sitio

Verificar siempre con cat -n el archivo después de cualquier pegado que incluya una URL seguida de ;.

  Prevención: para pegar bloques de configuración largos con URLs, usar un editor de archivos (nano, vim) en vez de un heredoc pegado directo en la terminal, o revisar el archivo resultante siempre.

7. El dominio muestra la app equivocada

El sitio carga, pero es el contenido de otro proyecto

Alto

Síntoma

El dominio resuelve y responde 200 OK, pero el HTML que devuelve pertenece a otra aplicación distinta a la que se acaba de desplegar.

Causa

En un servidor con varios proyectos, el dominio quedó asignado (en Dokploy/Traefik, o en un nginx externo) a una app anterior, y nunca se reasignó al proyecto nuevo.

Solución

Revisar en el panel del reverse proxy (Dokploy) qué app tiene asignado ese dominio, y cambiarlo al servicio correcto. Si es nginx externo manual, revisar:

ls /etc/nginx/sites-enabled/
grep -rl "mi-dominio.com" /etc/nginx/sites-enabled/

  Prevención: antes de asignar un dominio nuevo, buscar si ya está en uso en otro lado del servidor.

8. Error 502 Bad Gateway

Cloudflare (o el navegador) muestra 502

Alto

Síntoma

El dominio carga pero devuelve 502 en vez del sitio.

Causa más común

El proxy (nginx/Cloudflare) intenta conectarse a un puerto donde no hay nada escuchando — típicamente porque el contenedor del frontend no publicó el puerto al host que el nginx externo espera.

Solución

Verificar localmente primero, sin pasar por el dominio:

curl -I http://127.0.0.1:PUERTO

Si eso falla, revisar que el contenedor publique el puerto:

docker ps | grep nombre-del-contenedor
# la columna PORTS debe mostrar 127.0.0.1:PUERTO->80/tcp

Si se usa Cloudflare, revisar también el modo SSL/TLS: en modo Full o Full (strict), Cloudflare exige HTTPS en el servidor de origen — si el origin solo tiene HTTP, cambiar el modo a Flexible.

  Prevención: siempre probar con curl directo al puerto local antes de probar por el dominio — aísla si el problema es la app o el proxy.

9. Un contenedor entra en crash-loop (Restarting)

docker ps muestra "Restarting (1) X seconds ago" en bucle

Crítico

Síntoma

Un contenedor nunca queda en estado "Up" estable, se reinicia constantemente.

Causa

El proceso principal del contenedor termina con error al arrancar — casi siempre por configuración (variables de entorno, conexión a base de datos), no por el código en sí.

Solución

Nunca adivinar — siempre leer el log primero, es lo único que da la causa real:

docker logs nombre-del-contenedor --tail 50

El mensaje de error casi siempre apunta directo al problema (ver casos 1, 2 y 10 de este manual, los más comunes).

  Prevención: nunca reintentar un up -d --build a ciegas esperando que "esta vez funcione" — leer el log entre cada intento.

10. Falla el login pero el usuario "existe"

"Usuario o contraseña incorrectos" con las credenciales correctas

Medio

Síntoma

Las credenciales configuradas en el .env actual son correctas, pero el login sigue fallando.

Causa

Cuando la app crea un usuario inicial automáticamente al arrancar, eso pasa una sola vez (la primera vez que la base está vacía). Si hubo varios intentos de despliegue con distintas contraseñas antes de la definitiva, el usuario quedó grabado con una clave vieja que ya no coincide con el .env actual.

Solución

Confirmar si el usuario ya existe en la base:

docker exec -it nombre-db psql -U usuario -d basededatos \
  -c "SELECT id, username, created_at FROM users;"

Si existe pero con datos viejos, borrarlo y dejar que la app lo recree con la configuración actual:

docker exec -it nombre-db psql -U usuario -d basededatos \
  -c "DELETE FROM users WHERE username='admin';"
docker compose restart backend

  Prevención: definir la contraseña definitiva antes del primer arranque en limpio, para no tener que corregir esto después.

11. El servidor se queda sin espacio en disco

La app deja de guardar datos sin ningún error visible al usuario

Crítico

Síntoma

La aplicación "se cuelga" de a poco: dejan de guardarse registros nuevos, el login puede empezar a fallar, sin ningún mensaje claro en la interfaz.

Causa

El disco del servidor se llenó — cuando eso pasa, la base de datos deja de aceptar escrituras nuevas por completo, y suele afectar a toda la aplicación, no solo a la función que genera más datos.

Solución

Revisar el espacio disponible regularmente, no solo cuando ya hay síntomas:

df -h

Si un servicio de base de datos crece rápido con historial (posiciones, logs, eventos), diseñar desde el inicio una política de qué se guarda y cuánto tiempo — no guardar todo indefinidamente "por si acaso".

  Prevención: calcular el crecimiento esperado de la base de datos antes de elegir el tamaño del disco, y monitorear el espacio libre periódicamente, no solo al desplegar.

12. Se subió una contraseña o archivo secreto a git

Un archivo con claves reales quedó en el historial del repositorio

Crítico

Síntoma

Un .env, una contraseña o un archivo de notas con credenciales aparece en git status como listo para subir, o ya se subió.

Causa

El .gitignore no se configuró antes del primer git add, o se agregó un archivo nuevo con secretos sin revisar qué se estaba subiendo.

Solución

Si todavía no se hizo commit: sacarlo del staging y agregarlo al .gitignore.

git restore --staged archivo-secreto.env
echo "archivo-secreto.env" >> .gitignore

Si ya se subió (aunque sea en un commit viejo): la clave debe considerarse comprometida — no alcanza con borrarla del código, hay que cambiarla (nueva contraseña, nuevo token/hash) y recién después limpiar el historial si el repo es público.

  Prevención: crear el .gitignore como el primer archivo del proyecto, antes del primer git add — y revisar siempre git status antes de cada commit.

Checklist de diagnóstico rápido

  1. ¿Todos los contenedores están "Up" y no en "Restarting"?
    docker ps
  2. ¿Qué dice el log del contenedor que falla?
    docker logs nombre-del-contenedor --tail 50
  3. ¿El servicio responde localmente, sin pasar por dominio ni proxy?
    curl -I http://127.0.0.1:PUERTO
  4. ¿Las variables de entorno de los distintos archivos coinciden entre sí?
    grep -E "PGUSER|PGPASSWORD" .env backend/.env.production
  5. ¿Hay espacio en disco?
    df -h
  6. ¿El archivo de configuración que se editó a mano quedó como se esperaba?
    cat -n archivo
